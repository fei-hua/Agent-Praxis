## 四、C-c 候选设计（待人工选择其一后再实现）

### 候选 C-1：外部耗时资源 + 分支独占（结构性不可顺序完成）
```
任务结构：三个分支各自需要**独占一个外部资源**（例如各有一个只能被单个进程占用的锁文件/端口句柄，
          lock 由 fixture 提供并在运行时校验）；验收要求三个分支产物都正确且各自持有过独占资源。
为何 DIRECT 不再合理：顺序处理会在第二个分支处因资源占用规则失败（fixture 层面真实拒绝），
                       必须先规划分支并行/编排并管理资源竞争。
风险：需要 fixture 能真实模拟独占资源；实现复杂度中等。
```

### 候选 C-2：分支输入仅在各自运行上下文可读（信息不可一次性载入）
```
任务结构：三个分支的输入数据分散在三处，且每处输入含大量数据（例如各 10 万行日志），
          验收要求每分支输出精确统计；总计数据量明显超出单次上下文可靠处理量。
为何 DIRECT 不再合理：单上下文顺序处理会触及容量/可靠性上限，而分支委派（各自只读自己那份）
                       是工程上的默认做法。
风险：需谨慎控制"数据量"以免被指人为灌水；需要 fixture 生成数据而非 prompt 声称。
```

### 候选 C-3：分支互斥语义（同一结论的不同假设，必须分别验证后合并）
```
任务结构：同一问题的三种互斥假设（例如三种可能的根因），每种假设需要独立的验证脚本与证据；
          最终必须给出"哪一假设成立 + 另两个为何被排除"的合并结论。
为何 DIRECT 不再合理：三个假设的验证互相独立且都必须留下证据，
                       顺序处理会让"先入为主"污染后两个假设的取证（验收要求证据隔离：
                       每个假设的证据必须来自其独立的运行目录与独立日志）。
风险：需要在验收层真实校验"证据隔离"，否则 GT 又退化为"可顺序完成"。
```
