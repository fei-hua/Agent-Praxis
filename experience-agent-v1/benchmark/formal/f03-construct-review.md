## 二、构念层面发现（本次审查的核心产出）

### 1. C 类：把"可利用可分解性"当成了"必须采用分解策略"

```
可并行 ≠ 第一决策必须是 DELEGATE/PARALLEL/WORKFLOW
反例（C1）：一个 Agent 完全可以 直改 ping.js → 改 routes.json → 写文档 → 跑 verify
且三件事都很小 ⇒ DIRECT 同样是"最小充分"的首决策之一
现行做法把 DIRECT 排除在 accepted set 之外，等于额外测了一个因素：
  "模型是否认为小型多任务请求值得委派"
这与本实验真正要测的"经验是否改善工具/子代理使用"并不等价。
```

### 2. D 类：结构合理，但 prompt 把并行线索直接告诉了模型

```
D1/D2 的任务结构确实支持 PARALLEL/WORKFLOW（尤其 D1 有独立子包与独立检查器），
但 prompt 明确写出"互不共享文件""各带独立验收脚本""两份分析互不依赖"——
这正是并行分解最关键的判断信息，等于把答案放进题面 ⇒ 决策泄漏。
本质问题：D 类适合做"可分解任务"，但不适合做"无提示的 first-decision benchmark"。
```
